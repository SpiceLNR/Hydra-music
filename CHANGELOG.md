# Hydra Music changelog

**English** · [Русский](CHANGELOG.ru.md)

Versions before 1.0.0 were assigned retroactively from the development history: from the first
skeleton to the first release. Numbering `N.M.P`: `M` grows when a new feature appears, `P` grows for
fixes. 1.0.0 is the first release checked end to end on real devices (Android and Windows); from
here on the data format changes only with backward compatibility.

Dates (all in 2026) are the creation times of the change packages. For the earliest versions
(0.1–0.7) the contents were taken from the list of changed files, so the descriptions there are
shorter and less precise. “Not verified” means the change reached the user, but there is no
confirmation yet that it solved the problem.

Current version: **1.0.0**.

---

The app passes the language through the new bridge method `set_lang` at startup and on every language change.
- Network log lines written before a language change stay in the old language.
- Tests: every `tr`/`trf` string of the core and the bridge has an English and a Ukrainian translation, placeholders match, log detail lines keep the `#` mark; translation and substitution. Core tests do not change the process language (parallel tests share one process).

## 0.33.0 — November 5: formats — only those that play everywhere; tags of old tracks
- Video containers mkv, webm, mov and m4v are picked up (they play as audio on Windows and Android). The README promised this before, but the scanner took only mp4 from video formats.
- WMA, APE, WavPack (wv) and AIFF are no longer picked up: Android (ExoPlayer) cannot play them, so they ended up in the phone library silent. AVI is not added for the same reason. Tracks of these formats added earlier stay: the scanner does not treat them as missing, otherwise they would go to the trash on all devices.
- Once per library (marker `.hydra/tags-reread-1`) tracks without a title and artist in the database re-read their tags: before 0.32.2 the strict parser did not read files with a broken field, and such tracks showed the file name. What is found is recorded as a normal edit and goes to other devices; your own edits are not touched, files are not changed. In the author's library this gives titles to 9 MP3s.
- README: which formats are picked up, which are not and why, which can have tags written.
- Tests: video containers are picked up, formats Android cannot play are not; a known WMA track does not go to the trash; re-reading tags runs once and does not overwrite your own edit.

## 0.32.2 — November 5: tags are read from files with broken fields
- An MP3 with a broken ID3 field (for example, a year not of four digits) was not read at all: the strict parser rejected the whole file. The app showed the file name instead of the title, did not see the cover, and edits were saved in the app only. Now tags are read in relaxed mode (the broken field is skipped), and the format is detected by content, not extension. This affects reading at scan, covers and writing edits. In the author's library this was the case for 9 of 98 MP3s.
- Checked on the author's real files (m4a, mp3, flac and wav): title, artist and cover are read, written and survive reinstalling. `.m4a` files that contain Matroska/WebM (117 for the author, downloaded from YouTube) play, but the lofty library cannot write tags into them: their edits are still kept in the app (`meta.json`), as intended.
- Tracks already added do not re-read their titles: the fix applies to new files and edits.
- Test: an MP3 with the year “19” is read (title, artist) and an edit is written into the file.

## 0.32.0 — November 5: custom relay server, settings by sections (not verified)

Empty or “Default” means the n0 servers again; device lookup by key (n0 DNS) stays the same. If internet sync is off, the address applies when it is turned on.

- Settings redone: sections “this device”, “sync”, “library”, “window” (Windows), “updates”; one line per setting, values on the right. Long explanations under switches are removed: a note appears only when something is wrong (internet sync did not start, the core did not start, autostart was not enabled). The debug line “Sync core” is shown only on error; “Version”, “Updates” and “About” are merged into one line and a footer. The “Allow background work” button (Android) is visible only until allowed.
- Tests: relay address rules (no scheme, ftp, empty host are rejected); changing the relay restarts a real iroh node, the device address stays, a wrong address shows as an error, returning to the default servers.

## 0.30.0 — November 5: simpler, larger pairing QR code
- The pairing link in the QR code is shorter: the device key, the one-time secret and the internet address (32 bytes each) are written in base64url (43 characters instead of 64 in hex), and the standard port 47475 is omitted. A typical link is about 165 characters instead of 236; the QR code is version 8 (49×49 modules) instead of 10 (57×57): modules are larger, so the camera reads the code more easily and from farther away.
- The error correction level is unchanged: it was already the lowest (L, the `qr_flutter` default).
- Compatibility: the new version also reads old links (hex, with a port). Old versions cannot read the new link — both devices must be at least 0.30.0 (auto-update takes care of this).
- Tests: a short link is read without loss; a non-standard port is kept; an old link is understood; a damaged key is rejected; the link is shorter than before.

## 0.26.4 — November 5: PC installation no longer blocked by a busy folder

## 0.26.3 — November 5: auto-update on Android
- The Android app checks for a new version on start and every 6 hours: `version-android.json` from the `latest` release (CI publishes it after the APK: version, commit, size, SHA-256).
- A banner at the bottom of the home screen, above the player bar: “Version X is available” → “Download” with a progress bar, “Pause” (resumable) and “Stop” → “Install”. If music is playing, you are first asked whether playback may stop.
- The APK is downloaded into the app data folder (`update/`) and verified by SHA-256. “Install” hands it to the system installer via a PackageInstaller session (no FileProvider or new libraries). The first time, Android asks to allow app installs from Hydra Music (`REQUEST_INSTALL_PACKAGES`); the banner suggests tapping “Install” again. Cancelling in the system dialog brings back the “Install” button.
- After installation Android closes the app; you open it yourself. The downloaded APK is removed on the next start.
- The native part (the `hydra/update` channel in `MainActivity`) is written by `patch_android_manifest.py`.
- 0.26.3 is installed on the phone manually (0.25.4 lacks the mechanism). The real check is the 0.26.3 → next version update.

## 0.26.2 — November 5: installing an update on the PC starts the script
- 0.26.1 downloaded, verified and unpacked, but after “Install” the program closed and did not start again: the install script never ran (empty `install.log`). Cause: `Process.start(mode: detached)` in Dart starts the process with the `DETACHED_PROCESS` flag, and PowerShell 5.1 silently exits with it. Checked on the PC: with `CREATE_NO_WINDOW` the same script works.
- The script is now started by the core: a new bridge method `spawn_hidden` (`CREATE_NO_WINDOW`, the process outlives the app). Tests: the started process really runs (on Windows — PowerShell), invalid requests are rejected.
- The script itself was correct: started manually, it swapped the folder and started 0.26.1.
- The 0.26.1 → 0.26.2 update still uses the old launch: after “Install” the script must be run manually. The real auto-install check is 0.26.2 → next version.

## 0.26.1 — November 5: fixed hash in the Windows build description
- `version-windows.json` from 0.26.0 had an extra character before the SHA-256: on the Windows runner `sha256sum` escapes a path with backslashes. The app rejects such a description, so the update would never be found. Now the hash is computed from a stream, and CI checks its format before publishing.
- This is the first update that 0.26.0 on the PC should find and install by itself.

## 0.26.0 — November 5: auto-update on Windows
- The program checks for a new version on start and every 6 hours: it reads `version-windows.json` from the `latest` release (a direct link, so the GitHub API rate limit does not matter). Only CI builds check; local builds (`flutter run`, `local_build.bat`) do not look for updates.
- At the bottom of the panel, above the status line, a “Version X is available” banner appears with a “Download” button. During the download a progress bar is shown with “Pause” (resumable) and “Stop” (the partial file is deleted, “Download” again).
- After the download the SHA-256 is verified and the archive is unpacked into `app.new` next to the program folder while the program keeps running. Then an “Install” button; if music is playing, you are first asked whether playback may stop.
- Installation: the program starts a PowerShell script (no windows) and closes. The script waits for it to exit, renames `app` to `app.prev` and `app.new` to `app`, and starts the new version. If the swap fails, it puts the previous one back and starts it. Install log: `app.update\install.log`. The previous version is kept in `app.prev` until the next update.
- CI: the Windows archive is built with 7-Zip (`Compress-Archive` produced backslashes inside), and `version-windows.json` (version, commit, size, SHA-256) is published next to it. The archive is published before the description.
- Tests: version comparison, parsing `version-windows.json` with rejection of suspicious file names.
- The first update is installed manually: 0.25.4 does not have the mechanism yet. The check is the 0.26.0 → next version update.

## 0.25.4 — November 5: the APK is signed with the key from the secret
- The 0.25.3 APK from Releases did not install over the previous version: `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, signatures do not match. CI did not change. Fingerprints: 0.25.3 was signed with key `78a4fb1b…`, 0.25.4 with the secret's key `201d899e…`, and the version installed on the phone matched neither. So Gradle had never used the secret's key (it was placed in `~/.android/debug.keystore`): builds were signed with a debug key from the runner environment, which stayed the same until GitHub updated the `ubuntu-latest` image. That key is lost, so the app had to be uninstalled and 0.25.4 installed fresh once (phone data and pairing are lost; music, trash and `.hydra/` remain).
- The path to the key from the `HYDRA_KEYSTORE_B64` secret is now passed to Gradle explicitly (`HYDRA_KEYSTORE`, a block in `build.gradle.kts` from `patch_android_manifest.py`); both debug and release are signed with it.
- CI prints the SHA-256 fingerprint of the secret's key and of the APK signature and fails if they differ: such an APK does not reach Releases. In the main repository a build without the secret fails too.

## 0.25.3 — November 3: duplicates merge, covers appear on the PC
- A cover received from another device did not show on the PC: the “no cover” list was cached and not reset after sync. Now the cache is reset on every library refresh.
- Duplicates: two live entries with the same file and hash (left over from an old hash fix) are merged at scan. The entry with a title stays, otherwise the one with the smaller id (the same on all devices); the extra one gets a deletion marked `duplicate_of` in the journal. The file is not touched, and the entry does not go to the trash.
- Protection: deleting one of the entries sharing a file (including a deletion from another device) no longer moves the shared file to the trash.
- Tests: merging duplicates leaves the file in place; deleting one of two entries with a shared file does not take the file.

## 0.25.2 — November 3: sync right after your own edits
- Auto sync ran at most every 10 minutes per device and started nothing after edits. Now after your own edit (cover, title and artist, deletion, restore, moving a track, creating, renaming and deleting a playlist) a sync with the device currently online starts 8 seconds after the last edit. A series of edits is combined into one sync; if another one is running, a retry follows in 10 seconds (up to 6 times). The auto sync and “only while charging” settings are respected.

## 0.25.1 — November 3: covers for formats without tags
- Changing the cover of a file that cannot embed one ended with the error “tags: No format could be determined from the provided file”. Now the image (jpeg) is saved next to the music in `.hydra/covers/<hash>.jpg`, and an edit `{"cover": "<hash>"}` goes into the journal.
- The image travels to other devices over the same channel as files (as a “file” `cover:<hash>`); the hash is verified and the name is safe. If the cover can later be embedded in the file, the image next to the music is no longer used.
- After reinstalling the cover comes back: `meta.json` remembers which image belongs to which file (by hash), and `covers/` lives next to the music.
- The `cover` field takes part in journal compaction. Tests: a cover for a tagless file is stored alongside, replaced and survives reinstalling; the cover reaches another device.
- The journal compaction test on random histories now also generates cover edits and checks that the cover is the same after compaction.
- Known limitation: replaced images stay in `.hydra/covers` (~50–100 KB each); there is no automatic cleanup yet.

## 0.25.0 — November 3: title and artist edits survive reinstalling
- For formats that cannot hold written tags (and files where writing failed), title and artist were kept only in the journal in the app database. They synced between devices but were lost on reinstall. Now such edits are duplicated in `.hydra/meta.json` next to the music (key: file hash).
- When scanning after a reinstall, a new file with that hash gets the saved title and artist instead of its tags; a removed artist stays removed. Further edits go to other devices the usual way via the journal.
- Entries for tracks deleted forever are removed from `meta.json` at scan; entries for files the database does not know are left alone (they are needed after reinstalling).
- Tests: surviving a reinstall (twice in a row), a removed artist, cleaning up the entry of a deleted track.

## 0.24.0 — November 3: the trash is visible from all devices
- A device's trash now also shows tracks deleted on another device, if the retention period (30 days) has not expired. Such entries are labeled “file is on another device”. The file is not copied to every device: it stays where it lies in the trash.
- “Restore” on a device without the file returns the track to the playlist; at the next sync the device whose trash holds the file takes it out and sends it. If the file has already been erased there (manually or by age), the track stays in the playlist “waiting for the file”.
- The deletion date now comes from the time of the delete operation itself, not from when the device learned about it: it is the same on all devices, and an old history of other devices' deletions (older than 30 days) does not fill the trash.
- “Forever” and “Empty trash” still act only on this device.
- Core: `TrashItem.has_file`. Tests: a recent deletion from another device is visible and restorable from a third device; old history does not fill the trash.

## 0.22.2 — November 2: deadlock with files nobody has “by hash”

## 0.22.0 — October 30: operation journal compaction
- The journal drops operations fully overridden by later ones (old reorders, edits and moves of the same track, old playlist renames and list orders). The final state does not change, neither here nor on devices that receive the journal later; the newest operation of every device stays, so exchange between devices is not broken. The cause of the bloat: every playlist re-sort appended one reorder per track (a new phone received about 11 thousand operations for 609 tracks).
- Compaction runs after a library scan at most once a day and only when the journal has more than 1000 entries.
- Tests: 200 random histories give the same state before and after compaction; a compacted journal syncs with an old and a new device to the same result.
